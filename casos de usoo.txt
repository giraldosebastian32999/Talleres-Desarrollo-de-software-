CLAVE: PAGOS-1
TIPO DE INCIDENCIA: Historia
RESUMEN: Crear Cliente
--------------------------------------------------------------------
DESCRIPCION:

ID: CU-01
Nombre: Crear Cliente
Actor primario: Administrador del istema
Actores secundarios: Sistema de Notificaciones

Precondiciones:
- El administrador tiene sesion activa con permisos de gestion de clientes
- El documento de identidad no existe previamente en el sistema

Postcondiciones (exito):
- El cliente queda registrado con ID unico y estado "Activo"

Flujo principal:
1. El administrador selecciona "Crear cliente"
2. El sistema muestra el formulario (nombre, documento, correo, telefono, direccion)
3. El administrador diligencia los datos y confirma
4. El sistema valida formato y unicidad del documento
5. El sistema almacena el cliente y asigna un ID unico
6. El sistema de notificaciones envia un correo de bienvenida

Flujos alternativos:
1a. Importacion masiva por CSV: el sistema valida cada fila y crea multiples clientes en lote
3a. Guardado como borrador: el sistema almacena datos incompletos con estado "Incompleto"
3b. Registro asistido telefonicamente: un asesor diligencia el formulario en nombre del cliente

Excepciones:
4a. Documento duplicado: el sistema informa "El cliente ya esta registrado"
4b. Datos obligatorios incompletos: el sistema resalta el campo faltante y no permite continuar
6a. Fallo en el envio de notificacion: el sistema registra el cliente y reintenta el envio del correo

Reglas de negocio referenciadas:
- RN-01: El documento de identidad es unico por cliente
- RN-02: El correo electronico es obligatorio para notificaciones

1b. Cliente inactivo: el sistema rechaza la creacion
4b. Fallo de verificacion bancaria: no se crea la cuenta y se muestra el error
5a. Numero de cuenta duplicado (colision): el sistema genera un nuevo numero automaticamente

RESUMEN: Crear Factura
--------------------------------------------------------------------
DESCRIPCION:

ID: CU-13
Nombre: Crear Factura
Actor primario: Sistema de Facturacion del Proveedor (automatico) / Administrador (manual)
Actores secundarios: Sistema de Notificaciones

Precondiciones:
- El cliente y el servicio asociado existen en el sistema

Postcondiciones (exito):
- Se registra la factura con estado "Pendiente" y fecha de vencimiento

Flujo principal:
1. El Sistema de Facturacion del Proveedor envia los datos de consumo del periodo
2. El sistema calcula el valor a pagar y genera la factura
3. El sistema asocia la factura al cliente y a su cuenta de referencia
4. El sistema notifica al cliente sobre la nueva factura

Flujos alternativos:
1a. Factura manual por ajuste o reliquidacion
2a. Facturacion consolidada de varios servicios en una sola factura
1b. Recepcion de datos de consumo por lote (varios clientes a la vez)

Excepciones:
1c. Cliente inexistente: se rechaza la factura y se genera un log de error
2b. Datos de consumo invalidos (negativos o nulos)
4a. Fallo en la notificacion: la factura se crea igual y se reintenta el aviso

Reglas de negocio referenciadas:
- RN-12: Toda factura debe estar asociada a un cliente y una cuenta validos

ID: CU-19
Nombre: Eliminar (Reversar) Pago
Actor primario: Administrador del sistema
Actores secundarios: Sistema Bancario, Sistema de Notificaciones

Precondiciones:
- El pago existe y fue registrado por error o duplicado

Postcondiciones (exito):
- El pago queda "Reversado" y la factura vuelve a estado "Pendiente"

4a. Generacion de nota credito en vez de reversar
5a. Notificacion automatica al cliente sobre la reversion

Excepciones:
2a. Plazo vencido: se rechaza la operacion
4b. Fondos ya liberados: la reversion falla y se marca para gestion manual
3a. Motivo no especificado: obligatorio antes de continuar

Reglas de negocio referenciadas:
- RN-15: Un pago solo es reversable dentro de las 24 horas siguientes a su confirmacion

- La cuenta existe y pertenece al cliente autenticado

Postcondiciones (exito):
- Se muestra el saldo actualizado sin alterar el estado de la cuenta

Flujo principal:
1. El cliente selecciona la cuenta y solicita el saldo
2. El sistema valida que el cliente sea titular de la cuenta
3. El sistema consulta el saldo en tiempo real ante el Sistema Bancario
4. El sistema muestra el saldo disponible y la fecha/hora de la consulta

Flujos alternativos:
1a. Saldo consolidado de todas las cuentas del cliente
4a. Detalle de sobregiro para cuentas corrientes (saldo propio vs. cupo disponible)
1b. Consulta de saldo proyectado incluyendo pagos programados

Excepciones:
2a. Cuenta bloqueada: no se expone el saldo
3a. Fallo de comunicacion bancaria: se muestra el ultimo saldo conocido con advertencia
2b. Cliente no es titular de la cuenta consultada: acceso denegado

Reglas de negocio referenciadas:
- RN-16: El saldo consultado debe reflejar el core bancario en tiempo real, salvo contingencia

CLAVE: PAGOS-21
TIPO DE INCIDENCIA: Historia
RESUMEN: Procesar Pago
--------------------------------------------------------------------
DESCRIPCION:

ID: CU-21
Nombre: Procesar Pago
Actor primario: Cliente
Actores secundarios: Sistema Bancario, Sistema de Notificaciones

Precondiciones:
- El cliente esta autenticado y tiene al menos una factura pendiente
- La cuenta de origen tiene saldo (o cupo de sobregiro) suficiente

Postcondiciones (exito):
- La factura queda en estado "Pagada"
- Se genera un registro de pago con numero de referencia unico
- El saldo de la cuenta de origen se debita

Flujo principal:
1. El cliente selecciona la(s) factura(s) a pagar y la cuenta de origen
2. El sistema valida el saldo disponible en la cuenta
3. El sistema muestra un resumen para confirmacion
4. El cliente confirma la operacion
5. El sistema envia la orden de debito al Sistema Bancario
6. El Sistema Bancario confirma la transaccion
7. El sistema registra el pago y actualiza la factura a "Pagada"
8. El sistema de notificaciones envia el comprobante al cliente

Flujos alternativos:
1a. Pago parcial de la factura (queda en estado "Pago parcial")
1b. Pago de multiples facturas en un solo movimiento prorrateado
4a. El cliente cancela la confirmacion y el caso de uso termina sin cambios

Excepciones:
2a. Saldo insuficiente: el sistema informa y termina la operacion
6a. Fallo o timeout del Sistema Bancario: rollback y el pago queda "En proceso"
8a. Fallo en el envio del comprobante: el pago queda registrado pero se reintenta la notificacion

Reglas de negocio referenciadas:
- RN-14: Todo pago "En proceso" debe resolverse dentro de un plazo maximo
- RN-17: No se permite doble debito sobre la misma orden de pago

CLAVE: PAGOS-22
TIPO DE INCIDENCIA: Historia
RESUMEN: Obtener Pagos por Cliente
--------------------------------------------------------------------
DESCRIPCION:

ID: CU-22
Nombre: Obtener Pagos por Cliente
Actor primario: Cliente / Administrador del sistema
Actores secundarios: -

Precondiciones:
- El cliente existe en el sistema

Postcondiciones (exito):
- Se muestra el historial de pagos del cliente sin modificarlo

Flujo principal:
1. El actor selecciona al cliente (o accede a su propio historial)
2. El sistema recupera todos los pagos asociados al cliente
3. El sistema muestra la lista ordenada por fecha descendente

Flujos alternativos:
1a. Filtro por rango de fechas o estado
3a. Exportacion del historial a PDF o Excel
1b. Agrupacion de pagos por cuenta de origen

Excepciones:
2a. Sin pagos registrados: se muestra mensaje informativo
1c. Cliente inexistente
3b. Error al generar el archivo de exportacion

Reglas de negocio referenciadas:
- RN-03: Un cliente solo puede consultar su propia informacion, salvo el administrador
